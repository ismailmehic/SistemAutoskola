# PROJECT: Driving School Management System

You are a senior full-stack software engineer and software architect.

Build a complete, production-oriented, minimal, modern, responsive web application for managing a driving school in Bosnia and Herzegovina.

The application must be extremely simple to use. It is an internal administrative tool, not a large enterprise management system.

The most important feature is an electronic register book (E-Matična knjiga) that closely reproduces the official physical register book used by driving schools.

Other core features are candidate management, document management, payment tracking, instructor assignment, document-assisted candidate creation, and register archiving.

## 9. AUTOMATIC DOCUMENT DATA EXTRACTION

This is a critical feature.

The system must be architected to support automatic extraction of candidate information from scanned documents.

The workflow:

1. User clicks "Dodaj kandidata".
2. User uploads one or multiple documents.
3. Backend securely stores temporary uploads.
4. OCR service processes the documents.
5. Extracted information is mapped into candidate fields.
6. Frontend displays a review form.
7. User checks and corrects extracted values.
8. User confirms.
9. Backend creates the candidate.
10. Documents are linked to the new candidate.
11. User may optionally add the candidate to the active register book.

Never automatically save extracted personal information without explicit user confirmation.

### OCR architecture

Create an abstraction:

IDocumentExtractionService

Example method:

Task<DocumentExtractionResult> ExtractAsync(
    Stream documentStream,
    string contentType,
    CancellationToken cancellationToken
);

Create a structured result model.

Example fields:
- FirstName
- LastName
- FatherName
- DateOfBirth
- MunicipalityOfBirth
- JMBG
- Address
- MedicalCertificateNumber
- MedicalCertificateDate
- MedicalInstitution
- TheoryCertificateNumber
- TheoryCertificateDate
- FirstAidCertificateNumber
- FirstAidCertificateDate
- DrivingCertificateNumber
- DrivingCertificateDate

Include:
- Extraction confidence where supported
- Missing fields
- Uncertain fields
- Source document references

### Implementation strategy

Implement the complete review and approval workflow.

Start with a working local OCR provider where practical.

Keep the OCR provider replaceable through dependency injection.

Do not make the entire application depend on an external paid AI service.

If a reliable extraction provider is unavailable, provide a manual extraction fallback and clearly identify which parts are not automated.

Never simulate successful OCR by returning invented candidate data.

### OCR security

Treat uploaded documents as sensitive.

Do not send documents to third-party AI services without explicit configuration and authorization.

Never log extracted JMBG values or raw document contents.

Use temporary file cleanup.

Implement reasonable OCR timeouts and error handling.

The "Sve autoškole" option should show combined information.

When creating a new candidate or register book while "Sve autoškole" is selected, require the administrator to explicitly select a driving school.

Persist the selected school in frontend state and optionally localStorage.

Do not use localStorage for authentication tokens.

Backend APIs must receive or derive the selected DrivingSchoolId.

Never rely exclusively on frontend filtering.

## 4. CANDIDATE OWNERSHIP

Every candidate belongs to one driving school.

Add:

Candidate.DrivingSchoolId

A candidate must have a valid driving school.

Display the driving school name on the candidate profile.

Allow filtering candidates by driving school.

If transferring a candidate between driving schools is ever needed, implement it as a separate audited workflow.

Do not silently change the school of a candidate who already has official register entries.

## 5. REGISTER BOOK OWNERSHIP

Every register book belongs to one driving school.

Add:

RegisterBook.DrivingSchoolId

Each driving school can have its own register book for each year.

Example:

Autoškola ZNAK Sarajevo:
- Matična knjiga 2026
- Matična knjiga 2027

Autoškola 2:
- Matična knjiga 2026
- Matična knjiga 2027

Register books must never mix candidates from different driving schools.

When adding a candidate to a register book, validate on the backend that:

Candidate.DrivingSchoolId == RegisterBook.DrivingSchoolId

Archived register books remain accessible under their original driving school.

## 6. INSTRUCTORS ACROSS DRIVING SCHOOLS

An instructor may work with more than one driving school.

Create a many-to-many relationship between instructors and driving schools.

Use:

DrivingSchoolInstructor

Fields:
- Id
- DrivingSchoolId
- InstructorId

The administrator can assign instructors to one or more driving schools.

When assigning an instructor to a candidate, show instructors associated with that candidate's driving school.

A candidate may have:
- One instructor with 100% allocation
- Two instructors with a 50/50 allocation
- Other valid allocation percentages totaling 100%

Keep this functionality simple.

Do not implement instructor payroll.

4. Basic application settings

## 9. SECURITY

Although this application is private, it will be accessible through a subdomain on a Hetzner server.

Therefore, maintain:
- HTTPS
- Secure authentication
- Protected document storage
- API authorization
- Secure file uploads
- Database backups
- Document backups
- Audit logs for important changes

Private usage does not mean security can be ignored.

## 10. FINAL OBJECTIVE

Build the simplest possible application that allows one administrator to manage multiple driving schools efficiently.

The main workflow should be:

Select driving school
→ Add candidate
→ Upload documents
→ Review extracted information
→ Save candidate

→ Assign instructor
→ Track payments
→ Archive completed register books

All functionality must work across desktop and mobile devices.

Prioritize simplicity, reliability, and data integrity over unnecessary features.
